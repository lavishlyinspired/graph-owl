# Plan: Entity Resolution & Deduplication (Epic 17)

**Branch**: feat/entity-resolution
**Status**: Not started
**Depends on**: Epic 4 (`sameAs` in the graph), Epic 15 + 16 (two write paths make this necessary)
**Crate**: `graph-owl-resolution`

## Goal

One asset, one node, however many paths reported it. By Epic 21 there are six write paths — connectors, ingestion API, webhooks, streaming, declarative files, document extraction — each able to report the same real-world asset differently.

## Why this is a correctness requirement, not a feature

A duplicated asset silently halves every trust signal attached to it, splits lineage into two partial chains, and makes an agent's answer wrong in a way nothing surfaces. Exact-FQN matching handles the easy case and nothing else: a connector reporting `prod.sales.orders`, a webhook reporting `PROD.SALES.ORDERS`, and a runbook mentioning "the orders table" are one asset and three nodes.

It lands immediately after the second write path exists.

## Resolved decisions

1. **Merges are reversible.** `sameAs` records provenance — what matched, on what evidence, at what confidence, by whom. A wrong merge is splittable. An irreversible merge of two real assets is unrecoverable data loss.
2. **Blocking before comparison.** Pairwise comparison is O(n²) and unusable at 100k entities. Candidates are generated by blocking keys (normalized name, normalized FQN tail, soundex of name, parent scope) and only candidates are compared.
3. **Three confidence bands.** ≥0.9 auto-merge; 0.6–0.9 queue for review; <0.6 discard. Auto-merging at 0.7 will merge distinct assets, and a catalog that silently conflates two tables is worse than one with duplicates.
4. **Deterministic before probabilistic.** Normalized-FQN equality is checked first and short-circuits. Most duplication is case or quoting, and that must not depend on a similarity threshold.
5. **Mention resolution is a separate operation from entity dedup.** Linking "the orders table" from prose to a canonical entity (Epic 21) uses the same candidate machinery but a different decision rule — mentions are never auto-merged, only linked with confidence.

## Implementation reference

```rust
pub trait EntityResolver: Send + Sync {
    async fn candidates(&self, draft: &EntityDraft) -> Result<Vec<Candidate>, ResolveError>;
    async fn resolve(&self, draft: &EntityDraft) -> Result<Resolution, ResolveError>;
    async fn resolve_mention(&self, m: &TextMention) -> Result<MentionResolution, ResolveError>;
}

pub struct Candidate {
    pub entity: Uuid, pub fqn: String,
    pub score: f64, pub evidence: Vec<Evidence>,
}

pub enum Evidence {
    ExactFqn, NormalizedFqn, ExactName { scope: String },
    NameSimilarity { metric: String, value: f64 },
    StructuralOverlap { shared_columns: usize, total: usize },
    SameParent, SameSourceSystem,
}

pub enum Resolution {
    New,                                        // no candidate above threshold
    Existing { entity: Uuid, confidence: f64 }, // auto-merge band
    Ambiguous { candidates: Vec<Candidate> },   // review band
}

pub struct MergeRecord {                        // the reversibility contract
    pub id: Uuid,
    pub canonical: Uuid,
    pub merged: Uuid,
    pub evidence: Vec<Evidence>,
    pub confidence: f64,
    pub decided_by: Authorship,                 // Auto | Human | Agent
    pub decided_at: DateTime<Utc>,
    pub split_at: Option<DateTime<Utc>>,
}
```

### Blocking keys

| Key | Catches |
|---|---|
| `lower(fqn)` with quoting normalized | Case and quoting variants |
| `lower(name)` + parent FQN | Same table reported under a differently-named parent |
| Soundex/metaphone of `name` | Typos and transliteration |
| Sorted column-name hash | Same table renamed at the source |

A draft is compared only against entities sharing at least one blocking key. Keys are indexed; candidate generation is an index lookup, not a scan.

### Scoring

```
score = 1.0                              if normalized FQN matches (short-circuit)
      = 0.5 · name_similarity            (Jaro-Winkler)
      + 0.3 · structural_overlap         (Jaccard over column names)
      + 0.1 · same_parent
      + 0.1 · same_source_system
```

Pure function of two entity views — no I/O, exhaustively testable, which is why it lives in `graph-owl-resolution` rather than the adapter.

### `sameAs` in the graph

A merge asserts `(merged sameAs canonical)` and retracts the merged entity's own flakes, keeping them recoverable via time-travel (Epic 4). Epic 6's `sameAs` rule then makes the canonical entity inherit the merged entity's properties, so nothing is lost. A split retracts the `sameAs` and re-asserts from the merge record.

## Acceptance criteria

- [ ] Deterministic normalized-FQN matching short-circuits before scoring.
- [ ] Candidate generation is an index lookup, not a scan — verified by query plan.
- [ ] The three confidence bands behave as specified; nothing auto-merges below 0.9.
- [ ] Every merge writes a `MergeRecord` with evidence; every merge is splittable.
- [ ] Splitting restores both entities with their relationships intact.
- [ ] Ambiguous candidates queue for review with evidence shown.
- [ ] Mention resolution links without merging.
- [ ] Resolution runs on every write path, not just connectors.

## Slices

Every slice runs RED → GREEN → MUTATE → KILL MUTANTS → REFACTOR with implementation skills loaded first.

### Slice A: Deterministic matching

**Acceptance criteria**: `prod.sales.orders` and `PROD.SALES.ORDERS` resolve to the same entity; `service."my.db".schema.t` and `service.my%2Edb.schema.t` normalize identically; a genuinely different FQN does **not** match; normalization is a pure function with a documented rule set; deterministic match short-circuits — scoring is not invoked.
**RED**: Table-driven normalization tests including the quoted-segment case from Epic 2's tokenizer. A test asserting the scorer is *not* called on an exact match (call counter) — this is a correctness matter, not just performance, because a scorer bug must not affect exact matches. Mutator watch: case-sensitive comparison must fail; skipping the short-circuit must fail the call-count assertion.
**Done when**: criteria met, mutation report reviewed, commit approved.

### Slice B: Blocking keys and candidate generation

**Acceptance criteria**: four blocking keys computed and indexed on entity write; candidate generation returns only entities sharing a key; on a 100k-entity corpus, generation is an index scan (query plan asserted) and returns in < 50ms p95; an entity with no shared key produces zero candidates, not an error; blocking keys are recomputed on rename.
**RED**: Query-plan test asserting index use, not sequential scan — the difference between viable and unusable. A recompute-on-rename test: a renamed entity must be findable under its new blocking key. Mutator watch: a scan-based generator must fail the plan test; stale blocking keys after rename must fail the recompute test.
**Done when**: criteria met, mutation report reviewed, commit approved.

### Slice C: Probabilistic scoring (pure)

**Acceptance criteria**: score is a pure function of two entity views; each term isolated by a test holding the others equal; identical names in different parents score below identical names in the same parent; structural overlap uses column-name Jaccard, and 0 shared columns contributes 0 not a division error; score is in `[0,1]`; weights are configurable.
**RED**: One isolating test per term — the only way to prove a weight is applied. A zero-column edge case (empty Jaccard denominator). Mutator watch: a zeroed weight must fail its isolating test; an unguarded Jaccard divide must panic on the zero-column case.
**Done when**: criteria met, mutation report reviewed, commit approved.

### Slice D: Confidence bands and auto-merge

**Acceptance criteria**: ≥0.9 auto-merges and writes a `MergeRecord`; 0.6–0.9 returns `Ambiguous` and queues, creating nothing; <0.6 returns `New`; band boundaries are inclusive as documented and tested at exactly 0.9 and 0.6; auto-merge is disableable per deployment; a merge retracts the merged entity's flakes and asserts `sameAs`.
**RED**: Boundary tests at exactly 0.9 and 0.6. A test asserting the 0.85 case creates **nothing** — neither a merge nor a new entity — because a queued ambiguity that silently created a duplicate would defeat the epic. Mutator watch: `>` for `>=` must fail the boundary; auto-merging the review band must fail the creates-nothing test.
**Done when**: criteria met, mutation report reviewed, commit approved.

### Slice E: Merges are reversible

**Value**: The decision that makes auto-merge safe to enable.
**Acceptance criteria**: `POST /merges/{id}/split` restores both entities; both retain their own relationships, tags, and owners as they were before the merge; the split is recorded on the `MergeRecord`, not by deleting it; splitting an already-split merge → `409`; a split entity is excluded from re-matching against its former partner for a configurable cooldown, so it does not immediately re-merge; time-travel before the merge and after the split show equivalent state.
**RED**: The round-trip equivalence test — state before merge and after split must match, which is the reversibility contract. The cooldown test: without it, auto-merge re-merges what a human just split, which is the most frustrating possible behaviour. Mutator watch: deleting the merge record must fail the `409`; missing cooldown must fail the re-merge test.
**Done when**: criteria met, mutation report reviewed, commit approved.

### Slice F: Review queue

**Acceptance criteria**: `GET /resolution/queue` lists ambiguous pairs with evidence and scores, paginated; confirm merges with `decided_by: Human`; reject records the decision so the pair is not re-queued; rejection persists across re-ingestion of the same draft; queue is filterable by entity type and score range; bulk confirm/reject.
**RED**: A rejection-persistence test: reject a pair, re-run the ingestion that produced it, assert it is not re-queued. Without this the queue refills with the same decisions forever. Mutator watch: a rejection that only deletes the queue entry must fail it.
**Done when**: criteria met, mutation report reviewed, commit approved.

### Slice G: Mention resolution

**Acceptance criteria**: `resolve_mention` takes text, expected type, and surrounding context; returns ranked candidates with confidence; **never auto-merges** — mentions link, entities merge; a mention with no candidate above 0.5 resolves to `None` rather than guessing; context disambiguates ("the orders table in staging" vs "in prod"); resolution is recorded as a `mentionedIn` edge with confidence.
**RED**: A context-disambiguation test with two same-named tables in different schemas, asserting the contextual hint selects correctly. A test asserting no merge occurs from mention resolution. Mutator watch: ignoring context must fail the disambiguation; merging from a mention must fail — it would conflate an entity with a passing reference to it.
**Done when**: criteria met, mutation report reviewed, commit approved.

## Explicitly deferred (with destination)

- **ML-based matching** (learned similarity) → the scoring function is pluggable; revisit once the review queue provides labelled pairs.
- **Cross-type resolution** (a Table and a Topic being the same logical dataset) → same-type only for now.
- **Transitive merge closure** ("A=B, B=C ⟹ A=C") → Epic 6's `sameAs` rule handles the *inference*; automatic transitive *merging* is not planned, since one wrong link would cascade.
- **Coreference within a single document** → Epic 21 territory; this epic resolves mentions to entities, not mentions to each other.
